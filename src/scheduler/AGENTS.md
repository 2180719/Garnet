# scheduler

Cron jobs, heartbeats, one-shot reminders and script-only jobs. The scheduler only decides *when*; every agent run goes through the gateway and the normal agent loop.

- Public API: `Scheduler` (start, stop, tick, runNow, resume, cancel, isRunning), `NOTHING`, `HEARTBEAT_OK`, `quietReply`; `JobBook` (the job list: config jobs plus stored jobs, with validation, provenance and limits); `scheduleTool`; `parseWhen` and the `describe*` helpers (`when.ts`).
- Where jobs live: `config.json` jobs are the owner's and read-only here. Jobs created with the `schedule` tool, `garnet jobs add` or the dashboard are stored in the database (`agent_jobs`, validated with the same `jobSchema` on every read; an invalid row or a name clash with config is reported by `JobBook.problems()` and not scheduled). Each stored job records its origin (`agent` with session and conversation, or `owner` via cli/dashboard). The scheduler re-reads the list every tick, so changes from the CLI (another process) apply without a restart; a job deleted while it runs is cancelled (recorded `cancelled`, not a failure, no message).
- What a run does (exactly one per job): `instructions` run the agent in its own conversation (`job:<id>`) with the job's grant intersected with the owner's (jobs default to read-only) and its own budget; `message` is sent as is (no model call); `script` runs the command in the sandbox and never calls the model: non-empty stdout is sent (with `notifyWhen: on_change`, only when its hash changed), empty output stays quiet, a non-zero exit or timeout is a failure. Script jobs need the sandbox, which exists only when `exec` is not deny.
- Occurrences: an occurrence ID (`<job>@<scheduled time>`) is claimed in the database before a run, so a slot runs at most once across restarts. New config jobs start from "now" (no backfill); stored jobs start from their creation. Missed occurrences coalesce into one catch-up run (told it is late), or are recorded as `missed` when `catchUp` is false. A config `once` job whose time had passed when Garnet first saw it is recorded `missed`. A job never overlaps itself.
- Cost controls: disabled or paused jobs and the global switch never run; a pre-check (`file_changed`, `url_changed`) skips the model when nothing changed; a 24-hour token budget per job; 3 consecutive failures pause the job and notify the owner. A run cancelled because Garnet is shutting down is `interrupted` and does not count as a failure.
- Results: with `notifyWhen: on_change` the model replies `NOTHING_TO_REPORT` when there is nothing worth saying, and the owner is not messaged. OpenClaw's `HEARTBEAT_OK` counts too, at the start or end of a reply with at most 300 characters beside it (`quietReply`); around a longer report the token is stripped. Approval requests and failures are always sent. `main.ts` delivers through `gateway.notify`, which also records the text in the target chat's conversation.
- Time: jobs use their `timezone`, else the owner's (`config.timezone`, else the host's). Cron parsing and zones live in `config/cron.ts`. DST: cron times skipped by spring-forward never fire; a wall-clock minute repeated by fall-back fires once (its first instance), except for jobs whose hour field is `*`. One-shot local times (`localToUtc`) in a gap move forward by the jump (the tool tells the owner); repeated ones take the first instance.

## The `schedule` tool

- Actions: `create`, `list`, `update`, `pause`, `resume`, `delete`. `when` is natural language or cron (`parseWhen`, see `WHEN_HELP`): relative ("in 20 minutes"), wall clock ("at 17:30", "tomorrow 9am", "friday 18:00", ISO), recurring ("every 30 minutes", "every weekday at 9:15", cron). A bare time already past today means tomorrow; a one-shot in the past is refused.
- Permissions (`capabilitiesFor`): `list` needs none; changes need `schedule.edit` (ask by default); creating or changing a script job also needs `exec`, so the owner approves the exact command (`exec` is reported as the capability when it ties). The approval summary (`summarize`) states the schedule in words with the next run in the owner's zone, the full text/instructions/command, and the delivery chat.
- Rules for jobs Garnet creates: at most `scheduler.maxAgentJobs` (finished one-shots do not count), at least 5 minutes between runs, `schedule.edit` never granted to the job, and scheduled runs (`job:` sessions) cannot use the tool. Config jobs can be listed, paused and resumed, never changed or deleted. Delivery defaults to the chat the job was created in (resolved by the gateway's `ChatDirectory`, so a Discord DM's channel id is used, not the user id); outside a chat, the owner's most recent paired chat.
- Containment: the tool declares `schedule.edit`/`exec`, and every declared capability is checked with the session's taint (strictest wins), so after untrusted content changes need approval with the taint note. A job created or edited by a tainted conversation stores the sources in its origin (`JobBook.taintOf`) and every run carries them in (`gateway.chat(..., { taint })`), so its consequential actions keep asking.

Testing: `when.test.ts` (parsing, DST, descriptions), `kinds.test.ts` (one-shots, late and missed runs, message and script jobs, deletion while running, limits), `tool.test.ts` (approval text, permissions, script exec gate, job-session refusal), `scheduler.test.ts`, and `test/schedule-flow.test.ts` end to end.
