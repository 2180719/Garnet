# channels

Messaging-platform adapters that implement `ChannelAdapter` from `contracts/channels.ts`.

- Public API: `TelegramChannel` (long-polling Telegram bot, no dependencies beyond global `fetch`).
- Adapters only normalize a platform: they never own identity, routing, dedupe or durable delivery (the gateway does).
- Inbound is at-least-once: acknowledge to the platform (advance offsets) only after `await sink(message)` resolves. If the sink throws, stop the batch and retry later from the same offset.
- `send` never throws. It returns `{ status: 'failed', retryable, retryAfterMs? }`: rate limits, 5xx and network errors that certainly happened before the request reached the server (DNS, connection refused/unreachable, connect timeout, TLS; see `delivery.ts`) are retryable; blocked bot or bad chat is not. Return `{ status: 'uncertain' }` when the request may have been delivered but the outcome is unknown: timeouts, resets and unknown fetch errors, 502/504, and a success status with an unreadable body (the gateway will not resend it).
- Long messages: split with `splitText` and sent with `sendChunks` (`delivery.ts`). A failure before any chunk is out is returned for the gateway to retry; once a chunk is out, retryable failures of later chunks are retried in the adapter (bounded wait), then reported as a non-retryable failure naming how many chunks were delivered, because a gateway retry would resend the delivered chunks.
- `start` fails fast with `RubyError('config')` on a bad token. After start, errors (conflicts, outages) go to `health().lastError` and are retried with backoff; they never crash the process.
- `stop` must abort the in-flight long poll and wait for the loop to exit, so a restart does not hit a 409 conflict. It is idempotent.
- Never log or return the bot token; redact it from every error message.
- Tests are offline: inject `fetch` and `sleep`; no real timers above 50ms.
- Media: inbound files become `attachments` with an opaque `ref` (Telegram `file_id`, Discord CDN URL, signal-cli attachment id plus sender or group); the text is the caption or empty. Content with no file or text that a person sent on purpose (stickers, locations, contacts, polls) sets `unsupported` so the gateway can answer. `fetchAttachment(ref, { maxBytes, signal })` downloads with `readCapped` (the declared size and the streamed size are both checked) and rejects with an owner-readable reason. `send` uploads `attachments` first, one message per file, with the text as the last file's caption when it fits (else the text follows); each file is one unit of `sendChunks`, so partial-delivery rules are unchanged.
  - Telegram: largest `photo` size, `document`, `voice`, `audio`, `video`/`video_note`/`animation`; downloads via `getFile` and `/file/bot<token>/<path>` (bots may download 20 MB; errors are token-redacted). Uploads are multipart: `sendPhoto` for JPEG/PNG/WebP up to 10 MB, `sendVoice` for OGG, `sendAudio` for MP3/M4A, else `sendDocument` (50 MB); captions up to 1024 characters.
  - Discord: `attachments[]` (with `duration_secs` for voice messages), `sticker_items` as unsupported. Downloads only from `https://cdn.discordapp.com` or `media.discordapp.net`, without the bot token. Uploads are multipart `payload_json` + `files[0]` (10 MB, the limit for bots without a boosted server).
  - Signal: `dataMessage.attachments[]` (`voiceNote` → audio); downloads with JSON-RPC `getAttachment` (`{ id, recipient | groupId }` → base64 `data`); sends files as RFC 2397 data URIs (`data:<mime>;filename=<name>;base64,...`) in `attachments`, so the daemon need not share Ruby's filesystem (100 MB).
  - `UPLOAD_LIMITS` (index.ts) exposes the per-channel send limits for tools that queue files before a channel is running.
- Adding a channel: create `<name>.ts` with a class implementing `ChannelAdapter` (constructor takes options plus optional `fetch`/`sleep`), add a `<name>.test.ts`, export it from `index.ts`, and wire it in `src/main.ts` from config.

## Signal

- `SignalChannel` talks to a local `signal-cli -a +NUMBER daemon --http 127.0.0.1:8080` (`GET /api/v1/check`, SSE `GET /api/v1/events?account=<number>`, JSON-RPC `POST /api/v1/rpc`). Each SSE event is `event:receive` with data `{ account, envelope }` (a JSON-RPC `receive` notification is accepted too). The stream is reconnected when silent for 60 s (the daemon sends a keepalive every 15 s). No dependencies. The RPC endpoint is unauthenticated, so a non-loopback `baseUrl` must be https (else `RubyError('config')`).
- Chat ids: `group:<groupId>` for groups, otherwise the sender's number (or uuid). `externalId` is `<sender uuid|number>:<timestamp>`. Envelopes without `dataMessage.message` (receipts, typing, sync) and messages from the bot's own number are ignored.
- Inbound is NOT at-least-once. SSE has no durable offsets: the sink is awaited sequentially, a failing sink is retried 4 times with backoff, then the message is dropped and `lastError` is set. A crash or restart can lose messages (the daemon only replays its last ~1000 events to a `Last-Event-ID` reconnect within one daemon lifetime). The gateway must not assume Signal gives at-least-once.
- `health().ok` is true while the event stream is connected, or if traffic was seen in the last 2 minutes.
- Send errors: pre-connect network errors and 5xx (except 502/504, which are `uncertain`, like timeouts and resets) are retryable; JSON-RPC errors and per-recipient failures (unregistered, invalid group) are not, except NETWORK_FAILURE and RATE_LIMIT_FAILURE. A send that reached at least one recipient (e.g. some group members) counts as sent. `replyToExternalId` is ignored (Signal quoting needs the author).

## Discord

- `DiscordChannel` uses the bot gateway (global `WebSocket`, JSON, no compression, API v10) for receive and REST (`fetch`) for send. No dependencies. `start` checks `GET /users/@me` (401 → `RubyError('config')`) and `GET /gateway/bot`, then connects in the background; it does not wait for READY.
- Intents: GUILD_MESSAGES | DIRECT_MESSAGES | MESSAGE_CONTENT. The privileged Message Content intent must be enabled in the Developer Portal (Bot > Privileged Gateway Intents) or the gateway closes with 4014, which is fatal (`lastError` explains it, `health().ok` false). 4004 (bad token) and other non-reconnectable codes are fatal; everything else reconnects with backoff, RESUMEing when a session exists. A missed heartbeat ACK closes the zombie socket and resumes.
- Inbound maps `chatId` = channel id, `externalId` = message id, `isPrivate` = no `guild_id`. Messages from bots (including itself), webhooks and with empty content are ignored. Guild messages are passed through with `isPrivate: false`; the gateway ignores them for now.
- Inbound is NOT at-least-once (same as Signal): the sink is awaited sequentially, retried 4 times, then the message is dropped and `lastError` set. Messages sent while disconnected beyond a failed resume are lost.
- `send` splits at 2000 chars, sets `allowed_mentions: { parse: [] }` (model output never pings), replies via `message_reference` (`fail_if_not_exists: false`) on the first chunk, and sends a per-chunk `nonce` with `enforce_nonce`. `dedupesSends` stays false because that dedupe is short-lived and was not verified. 429 → retryable with `retryAfterMs` from `retry_after` (float seconds); 5xx and pre-connect network errors retryable; timeouts, resets, 502/504 and a success without a message id are `uncertain`; other 4xx not.
