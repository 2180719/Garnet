# runtime

The agent loop and task lifecycle.

- Public API: `Agent.run(sessionId, text | ContentBlock[], { signal, onEvent, source })` → `TaskRecord` (blocks carry attachments already stored by the media ingest; any `data` is stripped before the user message is persisted); `Agent.compact(sessionId, { signal })` → `CompactionOutcome` (compact now, regardless of the threshold; never while a task runs on that session); `LaneQueue` for one active run per session with a global cap.
- Loop: check cancel (a request cancelled before it starts records no user message) → persist user message → check cancel/budget → build context → stream model → persist assistant message → for each tool call persist intent (`tool_started`), execute, persist result → repeat.
- A turn with any attachment records an inherited `tainted` event per file (`file "name" sent in chat`), like `options.taint`, except a voice note the gateway marked `liveVoice` (recorded live by the paired owner in a private chat, per the channel's own voice-note flag; forwarded voice notes and audio files taint). User messages with source `notification` or `approval` never contribute owner URLs.
- Every model request (and the compaction request) goes through `prepareAttachments` with the model's `capabilities.media`, `loadAttachment` and `maxAttachmentsInContext`, so adapters only ever see attachment blocks with bytes they can send, or text.
- The runtime is the only writer of model/tool lifecycle events.
- Taint: before each round of tool calls the runtime derives `SessionTaint` from the log (`sessionTaint(events)`: `tainted` sources, URLs in the owner's messages, links untrusted tools reported) and passes it on `ToolContext.taint`. A result with `untrusted` appends a `tainted` event (once per source) right after its `tool_finished`, emits `{ type: 'tainted' }`, and later calls in the same round see it. Taint is session-wide and never cleared (compaction summaries can carry injected text); `/new` starts clean.
- Subagents (built: `subagents.ts`, tool `delegate_task`): `subagentFactory` returns, per tool call, a `SubagentRunner` bound to the calling session (`AgentDeps.subagents`, passed on `ToolContext.subagents`). The child is a normal session (title `subagent: ...`) run by an agent built by `main.ts` with the parent's policy and approver, a smaller budget, its own model (`resolve`) and depth + 1; nesting beyond `delegation.maxDepth` is refused. The session row records its parent (`sessions.parent_id`, `SessionStore.rootOf`), and `main.ts` resolves the conversation scope (connectors, skills, `session_search`) through the root, so a subagent has exactly its parent's chat scope. The child stops on the parent's signal or the tool call's own, and gets at most the parent's remaining wall time. Where approvals are deferred to a chat (no interactive approver), a child's needed approval is a refusal, because its session is not a chat. The task text is recorded with source `subagent`, which is not the owner's words. It starts with the parent's taint as described next, and `newTaint` (sources beyond the parent's) comes back so the tool can taint the parent. An approval a child needs cannot be given from inside it: it stops and the parent is told. Original design notes: start the child with `run(childSession, prompt, { taint: parentTaint.sources })`. Inherited sources are recorded as `tainted` events with `inherited: true` right after the user message, so the child is contained from its first call and URLs in its (model-written) prompt are not treated as the owner's. The delegate tool should mark its own output untrusted when the child's session is tainted, so taint flows back to the parent.
- Context: the system prompt (from `promptSections(namespace, sessionId, extras)`: memory snapshot, skills index, and for the onboarding session only the bootstrap prompt) and the tool schemas are frozen per session (`context_frozen`). Tools registered or changed later are not sent until the next freeze. Before a task, if the last request used ≥ `compactAtTokens`, the runtime summarizes older turns (keep-tail) with the frozen prompt and tools, records a `checkpoint`, and re-freezes both so memory and tool changes apply.
- Optional built-ins: `selectExtras(sessionId)` (wired in `main.ts` from config and the conversation's scopes) is called once, when a session's context is first frozen; the answer is recorded as `context_frozen.extras` and reused at every later freeze, including compaction, so a session's built-in skills and connectors never change (`/new` starts a session that asks again). `promptSections(ns, sessionId, extras)` gets the set; tools for which `connectorOfTool` names a connector are frozen in only when that connector is in the set (the executor already refuses tools outside the frozen set). Both per-session rules compose: the onboarding session still gets `set_profile` and the bootstrap prompt, and any session gets only its own connector tools.
- Time: with `timeZone` (the owner's, wired in `main.ts`), each user message is shown to the model with its send time; see `context`. The system prompt is not changed per turn.
- Retries: only `provider_transient`, only when no text was streamed yet, with backoff or `retry-after`, and never past the task's `maxWallMs` (a longer `retry-after` fails the task instead of holding the lane).
- Deadline enforcement: the task deadline (`started + maxWallMs`, moved forward by approval waits) is composed with the caller's signal (`AbortSignal.any`) for each model call, including retry waits, and passed on `ToolContext.deadline`, where the executor adds it to the tool's own timeout (after adding that call's approval wait). A call cut off by the deadline finishes the task as `budget_exhausted` with the same reason as the between-turn check, and a reply or tool round past the deadline does too (the reply stays in the log; its tool calls get a `budget_exhausted` result and do not run). Caller cancellation still wins.
- Token accounting: `TaskRecord.delegatedUsage` (in memory only) holds tokens spent for a task outside its own calls: subagents including their descendants (`SubagentParent.charge`; a child's budget is capped at `remainingTokens()`, so it cannot spend more than the parent has left) and side-model tools (`ToolContext.chargeUsage`, used by `vision_analyze`). `taskTokens(task)` (own plus delegated) is what the token budget and the scheduler's job accounting read. It is kept out of `usage` because those calls are already priced from their own task rows or `model_spend`.
- Time limit: `budget.maxWallMs` does not count time a tool call spent waiting on an interactive approver (`ToolResult.approvalWaitMs`, set by the executor); the clock and the retry deadline move forward by it. Deferred approvals (chat, API) end the task, and the resumed turn is a new task with a fresh clock; a grant expires after its ttl and `/approve` then says so.
- Spending cap: `deps.refuse()` (wired in `main.ts` from `budgets.dailyUsd` and the day's known cost) is checked at the start of `run`; a message finishes the task as `budget_exhausted` before any model call and without appending the user message. Script and reminder jobs never reach `run`.
- Tool calls from a `max_tokens` or `refusal` turn are never executed. A compaction summary that stopped at `max_tokens` is discarded (compaction fails; history stays whole).
- An unexpected exception (store failure, bug) marks the task `failed` before it propagates, so no task is left `running`.
- `LaneQueue` hands a finished job's slot straight to the next waiter, so the global cap holds.
- Statuses: `running`, `waiting_for_user`, `waiting_for_approval`, `completed`, `cancelled`, `budget_exhausted`, `failed`.
