# cli

The `garnet` command (`bin.ts` → `main.ts`). `garnet jobs` (in `admin.ts`) lists config, chat-made and CLI-added jobs with their schedule and next run in words; `add`/`edit` take natural schedules (`parseWhen`); `delete`/`edit` refuse config.json jobs. Commands: `setup`, `doctor`, `update [--check] [-y] [--ref] [--reinstall]` (`update.ts`), `sandbox check` (`sandbox.ts`: read-only probe of the configured backend, same check doctor runs), `init`, `chat [--fake] [--session <id>] [--inline | --fullscreen] [--plain] [--onboard]`, `wake [--fake]`, `config [--plain]` (no subcommand: the fullscreen browser/editor on a terminal, else `check`), `config check|show|explain|get|set|unset`, `sessions`, `secrets list|set|rm|import-env|keygen`, `help` (and the admin commands in `admin.ts`, `knowledge.ts`, `backup.ts`; `garnet help` lists them all). Also: `providers list|add|use|rm` (`providers.ts`; writes config.json, takes effect on the next start). `config get|set|unset` accept `providers.<name>.*` paths.

- `main(argv, io)` returns an exit code and writes through `io`, so it is testable.
- The CLI is a surface, not logic: it calls `createGarnet()` from `src/main.ts` and renders runtime events.
- Secret values are read from stdin (`Io.readSecret`; hidden on a terminal), never from argv, and never printed. `garnet secrets set NAME VALUE` is refused without echoing VALUE.
- `import.ts` wires `garnet import` (and the wizard's import step) to a Garnet instance: memory with raisable caps (`config.memory.*Chars`, the store is swapped for one with the new limits), jobs validated with `configSchema` before they are stored, pairings through the gateway store, and the registered tool names / secret names for skill checks. `garnet import` writes config immediately; the wizard stores changes in its draft (saved with the rest of setup) and passes its prompter as `ask` (`--import-raise-caps`, `--import-pairings`, `--import-persona`).
- `extensions.ts`: `garnet skills builtin|enable|disable|reset|effective` and `garnet connectors list|enable|disable|reset|effective`, each with `--channel <scope>` (validated with `SCOPE_RE`). Edits go through `setToggle` and are validated with the config schema before `writeConfig`; output says when changes apply (restart, then `/new`) and warns about missing secret names (never values), `net.fetch: deny` and overrides for channels that are off. `scopeChain` maps a `--channel` scope to the conversation key such a chat really gets (`conversationKeyFor`, so a routed chat resolves as its route) and calls the runtime's own `scopesForConversation`; output then uses `resolveScopes` like the runtime and says when a chat is routed (never a second copy of the resolution). `knowledge.ts` hands those `skills` subcommands (and any `--channel`) to it, and `skills list`/`show` include built-ins.
- `garnet pair add <channel> <id> [--name]` (admin.ts) pairs a known sender without a code; IDs are validated per channel (`validSenderId` from migrate). Paired identities are owners.
- `garnet service ... [--name <n>] [--force]` resolves the instance for this GARNET_HOME (`resolveService`); `install` refuses to take over a unit that runs another home unless `--force`. Doctor and setup use the same resolution.

## setup and doctor

- `setup/` holds `garnet setup` (and `garnet init`, which offers it on a terminal). `wizard.ts` is the flow; every question goes through the `Prompter` interface in `prompt.ts` and every side effect through `SetupDeps`, so tests script it fully. `command.ts` parses flags and wires real dependencies (the composition root, the service module, the importer).
- The model step edits the provider in use (`activeProvider`). For `local`, `openrouter` and `openai-compatible` it also asks `provider-name` (`--provider-name`): `default` edits the `model` block, any other slug adds or updates `providers.<slug>` and makes it active. Gemini is a choice of the `provider` prompt (`gemini`).
- `setup/sandbox.ts` holds the sandbox questions (`sandboxStep`: docker, ssh or local; for ssh the host, user, remote workdir, agent or key file, the passphrase secret NAME and host key policy). It takes and returns the `sandbox` config and asks for no secret value. The tools step runs it only when "Run shell commands" is ticked (`permissions.exec` is `deny` by default, so most first runs skip it). A script without `--sandbox` keeps the configured backend; flags: `--sandbox`, `--ssh-host`, `--ssh-user`, `--ssh-workdir`, `--ssh-auth`, `--ssh-key`, `--ssh-passphrase-env`, `--ssh-host-keys`.
- The wizard is split by job: `wizard.ts` (flow, model, persona, channels, save, service, pairing, summary), `shared.ts` (`SetupDeps`, `State`, validators, `heading`), `secrets.ts` (`lookup`, `chooseStorage`, `secretStep`, `checked`: every step that needs a key or token goes through `secretStep`), and one file per later step. Parts of setup are the `SECTIONS` table in `wizard.ts` (id, label, live hint, `run`, `extra`): each is a menu entry on a re-run, and the `extra` ones are the second half of a first run. Adding a part is one entry.
- First run: import, model, persona and time zone, channels, then one question (`extras`, `--extras more|defaults`) that gates the `extra` parts: tools, connectors and skills, voice notes (only when a channel is on), spending cap and dashboard. A script always runs them and every question keeps the current setting unless a flag says otherwise, so `-y` changes nothing it was not asked to.
- `tools.ts` (`--tools web,files,memory,reminders,messages,commands|none`): each ability is one permission. Ticked abilities keep their setting or start at `ask`; unticked ones become `deny` (`applyAbilities`). Web asks the search backend (`--web-search`, `--searxng-url`; Brave and Tavily keys go through `secretStep`), commands ask where they run (`sandboxStep`).
- `approvals.ts`: the approval-mode question (sensible defaults, ask about everything, a second model reviews, own rules file, never ask). The permission policy owns the setting; setup reads and writes it only through `SetupDeps.approvalMode` (`ApprovalBinding` in `shared.ts`: `read`, `write`, `options`, `available`), and skips the step while that is absent. It is not wired in `command.ts` yet. The mode names follow the policy's tentative `permissions.mode` (`default | ask-all | allow-all | custom | reviewer`, plus `permissions.rulesFile` and `permissions.reviewer.model`). Wiring it is one `approvalMode` entry in `defaultDeps` plus the `--approvals`, `--approval-rules` and `--approval-reviewer` flags (prompt ids `approvals`, `approval-rules`, `approval-reviewer`; `approvals-allow-all` confirms never-ask). Modes not in `available` are not offered.
- `integrations.ts`: connectors (`CONNECTOR_STEPS`, an optional bespoke step per connector; any other connector in `CONNECTORS` gets a generic step that prompts for each secret `CONNECTOR_INFO[name].secrets()` declares, so new connectors appear in setup on their own; bespoke: calendar feed address and GitHub token as secrets, GitHub repositories and write, weather place and units) and the built-in skills (`SKILL_HINTS` is typed on `BuiltinSkillName`, so a new skill must add a hint). A connector that needs the network turns `net.fetch` back to `ask` when it was denied, and says so. Flags: `--connectors`, `--skills`, `--github-repos`, `--github-write`, `--weather-location`, `--weather-units`. Secret values are entered at the prompt (or stored with `garnet secrets set`), never by flag.
- `voice.ts` (`--voice none|openai|groq|other|command`, `--voice-url`, `--voice-model`, `--voice-key-env`): speech to text for voice notes. A key offered for one service is never offered to another address. A `command` backend set in config is kept.
- `preferences.ts`: `timezoneStep` (asked with the persona; the wake-up chat asks it itself), and the spending cap (`--daily-limit`, skipped for the demo model and local servers) and dashboard (`--dashboard`, which also turns on the API; loopback only). `garnet dashboard` still prints the login link.
- Channels are one checklist, not one question each: `channelsStep` asks a `multiselect` with id `channels` (flag `--channels telegram,discord`, `none` for none), then runs each ticked channel's `setup` in turn. The channels are the `CHANNELS` table in `wizard.ts`; adding one is one entry (name matching a `config.channels` key, label, hint, `setup`). Enabled channels start ticked on a re-run; unticking one asks `disable-<name>` (default no; a script gets yes, so `--no-telegram` or leaving it out of `--channels` turns it off) and a declined one stays as it is. The per-channel flags `--telegram`/`--no-telegram` etc. still work: `AnswerPrompter.multiselect` treats a boolean answer named after a choice as adding or removing just that choice.
- `Prompter.multiselect` (`prompt.ts`): `TerminalPrompter` uses raw mode (Up/Down or k/j move, Space toggles, 1-9 toggle that row, `a` all/none, Enter confirms, Ctrl+C cancels and restores the terminal); marks are text (`[x]`), never color alone, so `NO_COLOR` works. Without a raw terminal it falls back to a numbered list answered with numbers on one line.
- On a terminal (stdin and stdout TTYs, `TERM` not `dumb`, no `--plain`/`--inline`) `setup` uses the fullscreen `TuiPrompter` (`tui/`); `TerminalPrompter` (line prompts) and `AnswerPrompter` (`-y`, flags, tests) remain the fallbacks and `-y` behaviour is unchanged. While the alternate screen is up the wizard's `io` is captured (`TuiPrompter.capture`): notes appear above the next question, and everything is replayed to the real `io` after the screen is closed, so next steps stay in the scrollback. `Prompter.review?` (implemented only by the TUI) shows the summary before the save step; declining writes nothing.
- Each prompt has a stable `id` that doubles as its `--flag` in non-interactive mode (`AnswerPrompter`). Adding a question: give it an id, a `default`, and an `auto` (what a script gets without the flag; optional steps must default to off), and add the flag to `FLAGS` and `SETUP_USAGE`.
- Nothing is written before the save step, except an import the owner applies (memory and skills go straight to their stores). Secrets go to the encrypted store or `<home>/env`, never config, and never into output. A new key file for the store must be outside `<home>`.
- Live checks (`checks.ts`) run only after the owner agrees, cost no tokens, and scrub the secret from every message. Tests inject `fetch`.
- The persona basics live between `<!-- garnet setup -->` markers in `config.persona`, so hand-written or imported text survives re-runs. The marker code is `readPersona`/`writePersona` in `src/config`; `setup/persona.ts` only holds `askBasics`, the three questions shared by the form and the onboarding fallback.
- `doctor.ts` is read-only and offline: it reports which secret names exist but never prints a value, never calls a provider, and probes the sandbox (Docker or ssh) only when `exec` is allowed and the backend is configured, never changes anything on the remote, and warns on `sandbox.ssh.hostKeyChecking = off`. Each finding has a fix. `--json` for scripts; exit 1 when anything fails. Built-ins: each enabled connector (fail when a required secret name is unset, warn when `net.fetch` is deny or `write` meets `message.send: deny`), each enabled skill (warn when a local skill shadows it), and overrides for channels that are off.
- Wake-up choice: in `personaStep`, when `deps.wake` exists, the prompter is interactive and the model is usable (demo, local, or a key already found) and `permissions["memory.write"]` is not `deny`, a `select` with id `onboarding` offers `form` (default, the existing questions) or `wake`. `wake` skips the questions, and `wakeStep` runs `deps.wake` (real: `chat --onboard`, plus `--fake` for the demo provider) right after save and before the service step (the service reads config once at start, so it must start with the persona and time zone the chat saved; pairing stays after the service); a failure only adds a "still to do" line. Non-interactive runs (`-y`) never ask and never chat; there is deliberately no flag for it.
- `update.ts` is `garnet update` ([docs/UPDATING.md](../../docs/UPDATING.md)). The install dir is derived from `import.meta.dirname`, never the environment. Every side effect (git, npm, node, service commands, fs, the confirmation, the lock) goes through `UpdateDeps`; tests use real git on a temp bare repo plus a fake runner for npm and node, never the network. Rules: fast-forward only (no `reset --hard`, `clean`, force); rollback is `git checkout [-B branch] <old>` plus `npm ci` when dependencies were touched; exit codes 0/1/2 and 10 for `--check` with an update available; the lock lives in `.git/` of the install, never in GARNET_HOME; the new unit file is read from the NEW code (`service show` subprocess) because the running process still has the old template; the shim is reported on, never rewritten. `garnet --version` (handled first in `main.ts`, before GARNET_HOME is read) is the smoke check.
- The installer (`install.sh` at the repo root) is POSIX sh. Check it with `sh -n install.sh`; see the root AGENTS.md.

## `garnet chat` (`chat/`)

`garnet chat --onboard` (alias `garnet wake`) is the first-run wake-up: a new session titled `ONBOARDING_TITLE` in a Garnet created with `onboarding: true` (this registers `set_profile`, unless `memory.write` is `deny`, in which case the chat refuses to start, and adds the bootstrap prompt to that session only). The wake-up chat is one session: `/new` and `/resume` are refused in both UIs (`CommandContext.onboarding`), so the tool set with `set_profile` and `OnboardingWatch` stay bound to that one session, and the CLI sends `KICKOFF_MESSAGE` so the agent speaks first (not echoed in the TUI). Both UIs take an `OnboardFlow` (`chat/flow.ts`): after every turn `OnboardingWatch.afterTurn` says continue (with a one-time "Tool check passed" note once `set_profile` really succeeded) or fall back. On fallback the plain chat asks the form questions inline from its own input; the TUI exits (terminal restored; the fullscreen UI leaves the alternate screen first and repeats the "Setup chat is stopping" line on the normal screen) and `chat()` asks them with a `TerminalPrompter`. Both save through `applyProfile`, so answers already saved by the agent are the form's defaults and the chat stays in the session log. The fallback form also asks the time zone. Leaving the chat with persona and time zone unchanged (and no successful `set_profile`) prints a "Still to do" line pointing at `garnet wake` or `garnet setup`. `--fake` plays `onboardingScript()`, and so does the `fake` (demo) provider in config when onboarding (`main.ts`), so `garnet wake` works on a demo setup. `--onboard` cannot combine with `--session`.

`chat/index.ts` picks the mode: the interactive TUI when stdin and stdout are both terminals (and `TERM` is not `dumb`, and no `--plain`), otherwise a plain line chat. The TUI is fullscreen unless `--inline` or `chat.fullscreen = false` (config); `--fullscreen` overrides config, and `--inline --fullscreen` is a usage error. `chat.mouse` (default true) is the starting mouse mode. `main.ts` only dispatches to it.

The two TUI surfaces share one controller (`app.ts`) and the same width-independent transcript blocks (`commit` records a renderer per block):

- Inline (`screen.ts`): committed rows go to the terminal's scrollback; the bottom rows are a live region. The conversation stays on screen after exit.
- Fullscreen (`fullscreen.ts`): the alternate screen. Every frame is composed by `layout.ts` from the status bar (`statusBar` in `render.ts`: name, model, session, state in words, taint, context, tokens, cost or `?`; it shrinks to one row on short terminals), the transcript viewport (`viewport.ts`: committed rows at the current width plus the live tail of streaming text, spinner and queued messages) and the dock (rule, input or approval choices, suggestions, `fullscreenFooter`). Any width change re-renders the transcript from its blocks; the view keeps its relative position. Scrolled up, new output does not move the view and the last row says `↓ new messages below`; sending a message, an approval arriving or being answered, End/Ctrl+End and scrolling to the bottom follow again. Transcript rows are capped (`MAX_ROWS`). On exit it leaves the alternate screen and prints one line on the normal screen with `garnet chat --session <id>` (not for the wake-up chat).

| File | Owns |
| --- | --- |
| `text.ts` | `sanitize` for untrusted text, grapheme-aware display width (CJK, emoji, ZWJ, combining marks), ANSI-aware word wrap that carries styles across rows, truncate, token/duration formatting. Pure. |
| `theme.ts` | The DESIGN.md palette as SGR styles. Truecolor when `COLORTERM` says so, else 256 colors; `NO_COLOR` keeps bold/dim/italic but no color. Pure. |
| `markdown.ts` | Line-oriented streaming markdown: headings, emphasis, inline code, links, lists and task lists, quotes, rules, fenced code (framed, not wrapped as prose), pipe tables (held until complete, then aligned). `push` returns final rows; `pending` the provisional partial line. Pure. |
| `keys.ts` | Raw input → key events: control bytes, CSI/SS3 with xterm modifiers, Alt as ESC prefix, kitty `CSI u` and xterm modifyOtherKeys (Shift+Enter), bracketed paste, F1-F4, mouse reports (SGR and X10: `wheelup`/`wheeldown`, other events `mouse`, never text), sequences split across reads. `pendingTimeoutMs` is the flush delay: 30 ms for a lone ESC, 150 ms inside a started sequence; on flush a sequence cut off after its parameters is dropped (never text) and its late remainder in the next read is swallowed, while a bare `ESC [` stays Alt+[. Pure. |
| `editor.ts` | Multi-line editor state and key handling (grapheme moves, word/line kills, history with the draft kept) and its wrapped layout with cursor position. Pure. |
| `commands.ts` | Slash command table, parsing (`//text` escapes a leading slash), suggestions and Tab completion (command names, `/resume` session ids), the shortcut list. Pure. |
| `render.ts` | Visual blocks: banner, user message, assistant rows, tool rows (running/done/failed in words, 3-line preview), approval prompt and choices, turn summary, footer, help (with a Scrolling section in fullscreen), resumed transcript, session totals; for fullscreen the status bar, scroll indicator and footer. Pure. |
| `screen.ts` | Inline surface: committed rows go to the scrollback once; the bottom rows (stream, spinner, input, footer) are redrawn in place with synchronized output. No alternate screen. |
| `fullscreen.ts` | Fullscreen surface: enters and leaves the alternate screen, sets SGR mouse reporting (1000 + 1006), draws whole frames row by row (only changed rows) with synchronized output. `FULLSCREEN_OFF` is the last-resort restore. |
| `layout.ts` | Splits the screen into status bar, transcript and dock (the dock keeps at most half; the status bar shrinks first) and maps the cursor. Pure. |
| `viewport.ts` | Scroll state: following the bottom, or pinned with a count of unseen rows; the visible slice with a row for the indicator; re-wrap and trim adjustments. Pure. |
| `app.ts` | The interactive controller for both surfaces: raw mode, key routing (fullscreen view keys first), turns and type-ahead queue, approvals, interrupts, resize, suspend, exit. |
| `actions.ts` | Executes slash commands against Garnet (shared by both modes). Results render at a given width, so they redraw cleanly after a resize. |
| `plain.ts` | Line mode for pipes: replies on stdout, prompts/tools/status on stderr, no escape sequences. |
| `history.ts` | Input history in `<GARNET_HOME>/chat_history.jsonl` (mode 0600, last 1000 entries; entries starting with a space are not saved). |

Behavior to preserve:

- Keys: Enter sends; Shift+Enter, Alt+Enter, Ctrl+J or a trailing `\` add a line; Up/Down browse history; Tab completes; Esc or Ctrl+C interrupts a running turn (a second Ctrl+C while interrupting quits); at the prompt Ctrl+C clears the input, and twice on an empty line exits; Ctrl+D on an empty line exits; Ctrl+L clears; Ctrl+Z suspends (stops the process group so `npm run` and the shell see it).
- Messages typed while a turn runs are queued and sent in order; an interrupt drops the queue.
- Approvals: `y` once, `a` always for the rest of this chat (for `exec`, only the exact same command), `n`/Esc deny. A request with `taint` (escalated because the session read untrusted content) offers only `y`/`n` and is never answered by an earlier "always". The footer shows `⚠ untrusted content read` and a row is committed when a new source taints the session. The full operation summary is printed (commands are never truncated). "Always" lives in memory for the chat process and session only; the policy in `config.json` is never changed.
- Slash commands exist only when backed by real behavior: `/help`, `/new`, `/sessions`, `/resume <id>`, `/attach <path>` (a file for the next message; accepts a pasted or dragged path with quotes, escaped spaces, `~` or `file://`; `/attach` lists, `/attach clear` drops; the turn goes through `MediaIngest`, and an unreadable file-only turn gets an honest answer without a model call), `/model` (read-only: shows the model and provider in use), `/provider [name] [model]` (see below), `/usage`, `/compact` (`Agent.compact`), `/expand [n]`, `/clear`, `/exit`.
- Swapping providers (`/provider`, terminal chat only): `/provider` lists, `/provider <name> [model]` calls `garnet.providers.use`. The swap is queued like any message, so it runs between turns and applies from the next model call: the session's frozen system prompt, tool set and event log are untouched (the log stays append-only; each `assistant_message` records the model id that wrote it, and adapters drop other providers' blocks on replay). It only lasts for this process and never writes config.json (`garnet providers use` does that). It is refused, changing nothing, when the key is missing, the name is unknown, or the model was injected (`--fake`). Pricing, the output cap, media capabilities and the context window follow the new provider; the footer, banner and `/model` show the provider name. A warning says to `/compact` when the conversation would not fit the new window. Gateway chats (Telegram, Signal, Discord) and the HTTP API have no swap: a channel message cannot choose where the owner's conversation and key are sent, so it takes a config change and restart.
- Model text, tool calls and results, approval summaries and errors are untrusted: pass them through `sanitize` (`text.ts`) before styling, so escape sequences are shown (`␛`) and never reach the terminal. The approval prompt must show exactly what will run.
- Status is always spelled out (`✓ done`, `■ interrupted`, `✗ failed (timeout)`), never shown by color alone. Unknown usage is `?`, never 0.
- Resize: inline, wider terminals just use the new width; narrower ones are cleared and the transcript is re-rendered from width-independent blocks, because a reflowing terminal pushes old live rows into scrollback where they cannot be erased. Fullscreen re-renders the transcript at any new width and redraws the whole screen.
- Exit always restores the terminal (raw mode off, bracketed paste and the kitty keyboard flag popped, cursor shown; fullscreen also turns mouse reporting off and leaves the alternate screen), including on SIGTERM/SIGHUP/SIGINT and uncaught errors (an `uncaughtExceptionMonitor` restores once, before Node prints the error, so the report is readable). Ctrl+Z leaves the alternate screen before stopping; SIGCONT re-enters it and redraws.
- Fullscreen scrolling: PgUp/PgDn a page; Shift+Up/Down or Ctrl+Up/Down half a page; the wheel three rows; Ctrl+Home/Ctrl+End top/latest (plain Home/End only when the input is empty, otherwise they move in the line); Esc back to the latest only when no turn runs and no approval waits (otherwise Esc keeps its meaning). F2 or Alt+M toggles mouse reporting: on, the wheel scrolls and most terminals select text only with Shift (Option in iTerm2); off, selection is normal. These keys work during an approval; y/a/n still answer it.

Testing: the pure modules have unit tests; `chat/chat.test.ts` drives the whole chat through a fake TTY and `test/vt.ts` (a minimal virtual terminal with the alternate screen, absolute cursor positioning and private-mode tracking, so tests can check what is left on at exit), in both surfaces (its `start()` adds `--inline` unless `fullscreen: true`), and checks the plain mode. To look at it by hand: `npm run garnet -- chat --fake` (fullscreen) or `npm run garnet -- chat --fake --inline`.

## Fullscreen setup and config (`tui/`)

| File | Owns |
| --- | --- |
| `fullscreen.ts` | `FullscreenSession`: alternate screen on/off (`FULLSCREEN_ON`/`FULLSCREEN_OFF`), raw keys through the chat `KeyParser`, resize redraw, the `Screen` contract (`state`, `update(state, key)`, `view(state, w, h)`), `wantsFullscreen`. `close()` is idempotent and also runs on process exit, SIGTERM and SIGHUP. |
| `layout.ts` | `renderPage`: header with `Step n of m`, text progress bar, body, rule and key hints; degrades with height (full, one-row header, body and hints only; the question is never dropped, notes go first). `inputWindow`, `listWindow`. Pure. |
| `prompts.ts` | Text, confirm, select, hidden secret and review screens: state, key handling (`updatePrompt`) and frames (`viewPrompt`). Pure. |
| `prompter.ts` | `TuiPrompter implements Prompter`; maps prompt ids to the progress stages (`stageOf`: Import & model, About you, Channels, Tools, Extras, Save, Finish). Ids that several steps share (`secrets`, `keep-*`, `check`, `retry-*`) stay in the current stage. |
| `config-fields.ts` | The field model: `fieldsFromSchema` generates the list from `configSchema.toJSONSchema({ io: 'input' })` (kinds: string, number, integer, boolean, enum, `list` of strings, `complex`), plus `getAt`/`setAt`, `displayValue` (redacts), `tryChange` (validates with `configSchema.safeParse`), `coerce` and `editElsewhere` (where to edit what the browser cannot). Pure. |
| `config-sections.ts` | How sections are presented: plain title, blurb and a live one-line summary in `SECTION_INFO`, in the order a new owner wants (`orderSections`). A section missing from the table still appears, titled by its key, so new settings need no edit here. Pure. |
| `config-browser.ts` | `garnet config`: the state machine and views. Sections with summaries (and a preview pane of the highlighted section from 100 columns), the field list, `/` search over names, descriptions and section titles, `c` the changes since the last save, enums pick, booleans toggle, strings and numbers edit, lists of text items (hosts, repositories, argv) add/edit/remove in place, lists with a fixed set of items (skills, connectors, escalated capabilities) are checklists. Every change is checked with `configSchema.safeParse` before it is kept, and save writes through `writeConfig`. Secret NAME fields show whether the name resolves (`✓ found`, `✗ not found`, `? store locked`; `secretStatusFor` in `index.ts`, names only). Tables and lists of objects are read-only and say which command edits them. |

Behavior to preserve:

- Esc or Ctrl+C cancels (setup rejects with a `cancelled` error, config asks before discarding changes); the terminal is always restored. Marks are text (`(•) Yes`, `[x] on`, `›`, `(changed)`), never colour alone; `NO_COLOR` keeps bold/dim only. Paste is accepted (newlines become spaces); unknown sequences, including mouse reports, are ignored; the wheel works through alternate-scroll (arrows).
- Secrets: the hidden input shows dots and a count, never the value. The config browser shows secret NAMES (`apiKeyEnv`, `tokenEnv`) only, hides and refuses to edit credential-looking string fields, and redacts displayed values.
- Adding a setting needs no change here. A wizard prompt needs an id (the stage map in `prompter.ts` falls back to the current stage for unknown ids).
- Tests drive `updatePrompt`/`viewPrompt` and the config `Screen` with scripted keys, and `TuiPrompter` with a fake TTY and `test/vt.ts`. No real terminal.
