# sandbox

Runs shell commands for the `exec` capability (`run_command` in `src/tools/builtin/exec.ts`).

- Public API: `Sandbox` (`run`, `check`, optional `cleanup`, `kind`, `isolated`, `networked`, `workspace`), `SandboxKind`, `DockerSandbox` (`containerUser`), `SshSandbox`, `LocalSandbox`, `createSandbox`, `assertSandboxReady`, `openSandbox`, `requiresIsolation`, `sandboxUser`, `canWrite`, `NOBODY`, and the ssh helpers `remoteScript`, `remoteRelativeCwd`, `shellQuote`, `validateSshHost`, `validateSshUser`.
- Adding a backend: implement `Sandbox` (reuse `supervise`, `OutputCollector`, `validateEnv` from `sandbox.ts` so timeouts, cancellation and per-stream output caps behave the same), add its kind to `SandboxKind` and one entry (`create`, `requireIsolated`) to the `backends` table in `factory.ts`, add its options to `SandboxOptions`, and map config in `sandboxOptions` (`src/main.ts`, which also resolves any secret by name). `check()` must be read-only and say how to fix a failure. Never fall back to another backend.
- `DockerSandbox` is the isolation boundary. Each run is a fresh `docker run --rm` with: `--network none` (unless configured `bridge`), memory/swap, CPU and PID limits, `--cap-drop ALL`, `no-new-privileges`, read-only root, a 64 MB `/tmp` tmpfs (nosuid, nodev), a non-root `--user` (below), `--pull never`, and only the workspace bind-mounted at `/workspace`. The docker client gets an allowlisted environment; the container gets `HOME=/tmp` plus explicit `NAME=value` variables only.
- The container **never runs as root**. `sandboxUser` picks, in order: an explicit `user` (config `sandbox.user`; uid 0 is a `config` error), the host uid:gid when Garnet is not root, the workspace directory's owner when Garnet runs as root and the owner is not root, else `65534:65534`. `--user` is set on every `docker run` (the only path that starts a container). Because files the container creates belong to that uid, the workspace stays writable for the owner; `check()` refuses (and says how to fix it: run Garnet as a regular user, `chown -R` the workspace, or set `sandbox.user`) when the container user cannot write the workspace, e.g. Garnet as root with a root-owned workspace. `canWrite` ignores supplementary groups because the container has none from the host. Caveat: when Garnet runs as root its own file tools create root-owned files that a non-root container can rename or delete (it owns the directory) but not edit in place; run Garnet as a regular user.
- `LocalSandbox` runs `sh -c` on the host with a minimal environment. It is **not** a security boundary (`isolated: false`): the command can do anything Garnet's user can. Only for owners who choose it explicitly.
- `SshSandbox` runs `ssh` (system client, `spawn` with an args array, no local shell) against `sandbox.ssh` host/port/user. It is `isolated: true` only in the sense that commands do not run on the Garnet host; **the boundary is exactly as strong as the remote account** (the command can do anything that account can, and the remote can reach a network, so `networked: true` and output is untrusted). Say so wherever it is described; recommend a dedicated unprivileged account or a disposable VM.
  - Client options: `-F /dev/null` (ignore `~/.ssh/config`, which can run local commands via ProxyCommand), `BatchMode=yes`, no password or keyboard-interactive auth, `StrictHostKeyChecking` from `hostKeyChecking` (`strict` = `yes` by default, `accept-new`, `off` = `no` with `UserKnownHostsFile=/dev/null`), `ClearAllForwardings`, `ForwardAgent=no`, no X11, no multiplexing, `IdentitiesOnly` with `-i` for a key file, `IdentityAgent=none` unless `agent` is on, `ConnectTimeout`, keepalives, `-T`, then `-p`, `-l user`, `--` and the host. Host, user, port, key and known_hosts paths and the remote workdir are validated before anything is spawned (a host or user cannot start with `-`, contain `@`, `:` or whitespace; paths are absolute without newlines, commas or quotes).
  - The ssh client's environment is allowlisted (`PATH`, `HOME`, `LANG`, and `SSH_AUTH_SOCK` only with `agent`). A key passphrase is passed by value from the composition root, never read here: it goes to ssh through a 0700 temp dir with a static askpass script that prints `$GARNET_SSH_PASSPHRASE` (`SSH_ASKPASS_REQUIRE=force`, `BatchMode=no` because BatchMode skips passphrase keys; password and keyboard-interactive stay off), removed after each run. Never in argv, config or logs.
  - The remote side receives one word, `sh -c '<script>'`. `remoteScript` single-quotes every dynamic part (workdir, cwd, env values, command); env names are validated first. The script resolves the workdir with `pwd -P`, `cd`s into the relative cwd, and refuses (exit 125, nothing run) when the real directory is outside the workdir (symlinks included), then `exec`s `sh -c <command>`. The local `cwd` check is lexical (`remoteRelativeCwd`: absolute paths and `..` escapes are `denied`), because the remote tree is not the local workspace; the local `workspace` is only the root the exec tool compares against its session.
  - Timeout or abort kills the local ssh client (closing the connection). Remote processes get the usual dropped-login hangup/SIGPIPE; one that ignores both can outlive the run, so the account's own limits are the backstop (documented, not hidden). Exit 255 gets a note that it may be the ssh connection failing.
  - `check()` is read-only: key file readable, agent socket present, then `cd <workdir> && pwd -P` over ssh (nothing else). Failures name the fix (host key not known, key refused, name not resolved, timeout, missing workdir, ssh not installed).
- Never fall back from an isolated backend to `local`. An unavailable backend is a `config` error (`assertSandboxReady`, and `run_command` checks on first use).
- Invariants: no host shell (`spawn` with an args array); `cwd` resolved with `resolveInWorkspace` and must exist; stdout/stderr each capped at `maxOutputBytes` (head kept, rest drained); on timeout or abort the container is `docker kill`ed (retried until the client exits, since it may still be starting) and then `docker rm -f`ed, so no container outlives `run()`. Local runs kill the whole process group, also after a normal exit.
- `run()` never pulls images; `check()` reports how to pull a missing one. `DockerSandbox.cleanup()` removes containers labelled for this workspace left by a crash.
- Tests: `ssh.test.ts` injects a fake `spawn` (exact ssh argv, env allowlist, quoting, timeouts, passphrase helper, check failures) and also runs the generated remote script under a local `sh` to prove cwd containment and that hostile text is never executed; it never starts ssh or contacts a host. `sandbox.test.ts` uses a fake `spawn` (exact argument list, the `--user` choice for regular and root hosts, no env leakage, kill paths). `docker.test.ts` runs against real Docker (as root it hands the temp workspace to uid 1000, like an owner would) and skips with a reason when the daemon or `busybox` image is unavailable.
- Must not: decide policy (the executor does), or read config (the composition root passes options).
