# tools

Tool catalog and execution.

- Public API: `ToolRegistry` (register, schemas), `ToolExecutor` (execute), built-in `fileTools`, `execTool`, `readArtifactTool`, `webFetchTool`, `webSearchTool` (+ `searchBackend`), `WebFetcher`, `isPublicAddress`, `htmlToText`.
- Execution order: deterministic repair (`repair.ts`: exact-match-after-normalizing tool names, JSON-string arguments with fences or trailing commas; never guesses arguments) → look up → validate input with zod → compute targets → policy (with targets and the session taint) → approval → run with timeout and cancellation → oversized output saved as a session-scoped artifact (`read_artifact`) with a head returned. Repairs are recorded on the result and noted to the model; history is never rewritten.
- Object inputs are validated strictly: an unknown argument is an `invalid_input` error naming it and the allowed ones, never silently dropped (a schema with its own catchall keeps it). Only the top level is made strict; nested objects follow their schema.
- `bind(input, ctx)` (optional): resolves what would resolve late (a relative time, a recipient alias) right after validation; the bound input is what is authorized, shown, hashed into the grant and run. `BindMemo` keeps the resolution per session so the call repeated after an approval gets the same values (expires after an hour, dropped on run, lost on restart: a miss just asks again).
- Tool-level failures never throw; they return `{ status: 'error', category, content }` with a message that tells the model how to correct itself. A failed, denied, timed-out or cancelled operation is never an `ok` result: a tool that ran but did not succeed returns `ToolOutput.error` (e.g. `run_command` on timeout) and keeps its output. A thrown approver becomes an `internal` error. Output limiting happens after the run, and an artifact-store failure falls back to plain truncation, so a tool that ran is never reported as failed.
- Per-call permissions: a tool may set `capabilitiesFor(input)` when what it needs depends on the input (`schedule`: nothing to list, `schedule.edit` to change, plus `exec` for a script job). Each is checked with targets and taint; the strictest verdict wins (a taint escalation anywhere marks the approval as tainted); an empty list needs no permission. `summarize(input, ctx)` replaces the generic approval text and must show everything consequential in full.
- Adding a tool: create a `ToolDefinition` under `builtin/` with a precise description, a zod input schema with `.describe()` on fields, the narrowest `capability`, `targets` for scoped checks, and tests. Register it in `src/main.ts`.
- Untrusted output: a tool that brings outside content into the context sets `untrustedOutput: true` (every result of a run, errors included, then carries `untrusted`) or returns `ToolOutput.untrusted` per result (`{ source, links }`; `links` are URLs found verbatim in the content, which policy may let a tainted session fetch). `run_command` marks its output untrusted (`command with network access`) when the sandbox has a network (docker `network` not `none`, or the local backend); isolated docker with no network stays trusted. Future MCP, email and webhook tools must do this.
- Web (`web/`): `WebFetcher` is the only HTTP client tools use. Per hop it allows http(s) without credentials, resolves the host once, refuses if any address is not public unicast (`address.ts`: private, loopback, link-local, CGNAT, multicast, reserved and documentation ranges, IPv4 embedded in IPv6 forms), connects to that pinned address (no rebinding window), re-checks every redirect, drops caller headers on a cross-origin redirect, caps decompressed bodies and has one deadline. It runs in-process (the command sandbox has no network) and does not use HTTP(S)_PROXY. `trustedOrigin` lets an owner-configured endpoint (a self-hosted SearXNG) be private. `web_fetch` (`fetch-tool.ts`) turns HTML into Markdown with `html.ts` (a small linear tokenizer: drops scripts, styles, hidden elements, nav and page chrome, prefers main/article, strips invisible Unicode) and reads text types; other types are an error. `web_search` (`search.ts`) has backends `duckduckgo` (keyless HTML page, unofficial), `searxng`, `brave`, `tavily` (keys resolved by secret name at call time); its target is the backend's fixed endpoint.
- Names are `snake_case`. Keep descriptions short; they are sent on every request.
