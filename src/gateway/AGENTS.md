# gateway

The single source of truth for who may talk to Ruby, which conversation a message belongs to, and whether a reply was delivered.

- Public API: `Gateway` (start, stop, receive, chat, deliver, notify, health, approvePairing), `approvePairing(store, code)` for other processes, `ApiKeys`/`RateLimiter`, `ApiServer`, `ChatDirectory`, `sendMessageTool`, `assertSendAllowed`.
- Inbound: channel → `receive` persists to the inbox (deduped on channel/account/chat/external ID) → `dispatch`: group chats ignored; unknown senders get one pairing code per code lifetime; chat commands; otherwise queued on the conversation's lane.
- Unsupported content: a message with `unsupported` set (a sticker, a location, a poll: content with nothing to download; files are `attachments`) is persisted with its caption or a `[kind]` placeholder and answered right in `receive` with a short "I can't … yet" reply (pairing prompt for unknown senders, nothing in groups). It never reaches the model. The same wording answers files when media handling is off.
- Chat commands: `/start`, `/help`, `/new`, `/stop`, `/retry` (re-runs the newest owner message, wrapped in a note saying so, since the log is append-only; refused while a task runs), `/usage` (alias `/cost`, matching the terminal chat), `/status`, `/approve`, `/deny`. Commands never call the model, except `/retry` and approvals, which resume work.
- Notifications: `notify(target, text, record?, attachments?)` queues through the outbox; with `record: { from, skipSession? }` it also appends the text to the target chat's conversation (`ChatDirectory.record`: a `user_message` with source `notification`, marked as not written by the owner), on the conversation's lane so it never lands mid-turn. This is the only recording path: job results (every kind), `send_message` and nothing else. Returns the delivery ID. In processes without a gateway (terminal chat, CLI) `main.ts` queues and records directly.
- Conversations: `routes` in config link chats into a shared conversation; otherwise each chat is its own. `/new` rebinds the conversation to a fresh session.
- Approvals: `persistentApprover` persists an `ask` operation with a short code and pauses the task. `/approve <code>` or `/deny <code>` from any paired chat resumes the conversation that asked; an approval is a single-use grant for that exact tool and input (hashed), so changed arguments must be approved again. Grants expire.
- Outbound: every reply goes through the outbox, delivered in order per chat (a later reply waits while an earlier one to the same chat is retrying). Delivery retries with backoff or `retryAfterMs`, then fails. A message caught mid-send by a restart is marked `uncertain` unless the channel dedupes sends; it is never blindly resent. The same holds for a `send` that returns `{ status: 'uncertain' }`, throws, or does not settle within `sendTimeoutMs`.
- Recovery: tasks left `running` are failed and the sender is told, rather than replaying work that may have had effects. On start, inbound messages are persisted but not dispatched until every channel has started; then the pending backlog is dispatched in arrival order, so a new message cannot overtake an older one.
- Cancellation: every running task (channel or `chat()`) is registered per conversation, so `/stop` and `stop()` can cancel it.
- HTTP API: off by default; `listen` refuses a non-loopback host without an active key. Every route but `/health` needs `Authorization: Bearer ruby_<id>_<secret>`. Scopes: `chat`, `read`, `admin` (admin implies all). Keys are stored as salted HMAC-SHA256 hashes and compared in constant time. Each authenticated request is rate-limited per key and written to `api_audit`; failed authentications are audited at a limited rate (per IP and overall), keyless traffic (health, static files, demo, unknown paths) is not, and rows older than 90 days or beyond 100k are pruned hourly. Request bodies are capped (1 MB) and must arrive within 30 s (408 and connection close otherwise). With `trustProxy`, the client IP is the rightmost `X-Forwarded-For` entry. A `RubyError('conflict')` maps to 409.
- `/v1/chat/completions` is OpenAI-compatible, but Ruby keeps state server-side: only the newest user message is used, in the conversation named by `X-Ruby-Conversation` (default `default`) for that key.
- Delivery targets (`directory.ts`): `ChatDirectory` knows which chat a session belongs to (its conversation key; for a shared route, the chat that wrote last) and which private chats belong to paired identities (from real inbound traffic, so a Discord DM's channel id is used rather than the user id). Targets are only ever paired chats: "here"/omitted, "owner" (most recent), a channel, or `channel:<sender or chat id>`.
- `send_message` (`send-tool.ts`): capability `message.send` (ask by default; escalated after untrusted content); the approval shows the target and the full text; at most `gateway.messagesPerHour` per rolling hour across all chats, shared with `send_file` (`assertSendAllowed`, counted durably in `sent_messages`); the sending conversation is not re-recorded.
- Media: a paired sender's attachments are downloaded in `process` (never for unpaired senders or groups), refused before download when the platform's declared size exceeds `media.maxBytes`, then stored and described by `MediaIngest`. When a message has no text and nothing readable (a voice note with no transcription, an image for a text-only model, a failed download), the gateway replies honestly and does not run the model. Without `media` (media.enabled false) files get the unsupported-content reply for their kind, and a caption is not acted on alone. `/stop` while files download or transcribe answers "Stopped.". `chat()` takes `{ text, files }` for the API; unreadable input is a `RubyError('invalid_input')` (HTTP 400, or a streamed answer once headers are out). `notify(target, text, record?, attachments?)` can carry outbound attachments, which ride the outbox like text.
- `/v1/chat/completions` accepts `image_url` and `file` parts as base64 data URLs only (never fetches a URL: an `http(s)` URL is a 400 `unsupported_content_type`), other part types are a 400, and the body cap for this route is `maxChatBodyBytes` (set from `media.maxBytes`).
- `/v1/chat/completions` is OpenAI-compatible, but Ruby keeps state server-side: only the newest user message is used: its text parts plus `image_url`/`file` parts as base64 data URLs (see Media below); `content` may be a string, an array of parts, or null in history. The conversation (per key) is, in order: `X-Ruby-Conversation`; `X-OpenWebUI-Chat-Id` (hashed; Open WebUI's temporary `local…` ids are skipped); else a hash of the key, the `user` field and the chat's first user message, which stays fixed across turns for clients that resend history. `user` only scopes that hash: it names a person, so keying on it alone would merge their chats. Consequence: a client that sends only its newest message without a header starts a new conversation per message; such clients must send `X-Ruby-Conversation` (the dashboard does). When a derived conversation is new but the request carries earlier messages (a chat begun elsewhere, or an edited first message), they are replayed once as a marked transcript (last 12k chars).
- Open WebUI background tasks (prompts starting `### Task:` with a `<chat_history>` block: title, tags, follow-ups, queries, image prompt, autocomplete) are answered in `http.ts` with the JSON shape the template asks for (a title from the last user line, `["General"]` tags, empty lists), with no model call and no conversation.
- `/approve CODE` and `/deny CODE` sent to the API decide approvals raised in that same API conversation only (`Gateway.approveInConversation`); others are refused with a pointer to their own chat or the dashboard.
- Streams send `: keepalive` SSE comments every 15 s while a task runs. CORS is off unless `api.corsOrigins` lists exact origins; then only `/v1/chat/completions` and `/v1/models` get CORS headers and a keyless preflight answer; the request itself still needs a key.
- Must not: call models or tools directly (only through `Agent`), or log secrets.
