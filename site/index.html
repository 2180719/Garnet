A personal agent
you can read.

Garnet lives on your own computer or server and answers on Telegram, Signal, Discord, in your terminal, or over an API. It is small enough to audit, locked down until you say otherwise, and plain about what it can and cannot do.

Why Garnet

Small. Secure by default. Honest.

Personal agents get a lot of access to your files, accounts and chats. Garnet is built on the idea that you should be able to see what it does and decide what it may do.

  1. Small enough to read

    One TypeScript codebase, run directly by Node with no build step, SQLite for storage, and two runtime dependencies. Every module has a short guide for people and agents. Its memory is two Markdown files you can open in an editor.

  2. Closed until you open it

    Writing files, sending messages, fetching URLs, changing memory and scheduling all ask first. Running commands is denied. The API will not listen on a public address until an API key exists.

  3. Honest about itself

    Garnet reports what it did and did not do, says when it cannot read a voice note instead of going silent, and this page lists what is not built yet. Pre-release means pre-release.

What it does

Everything here is built and tested.

The automated suite runs offline against a fake model and fake channels. Features marked live-tested have also been run against real services; the rest still need that.

Where you talk to it

  • Telegram, Signal (through signal-cli) and Discord
  • A full-screen terminal chat with a status bar, a scrollable transcript, streamed Markdown, tool rows, approvals and a multi-line editor (or inline, in your scrollback)
  • An opt-in web dashboard and an OpenAI-compatible API for Open WebUI, LibreChat and friends
  • Chat commands: /new, /stop, /retry, /usage, /status, /approve, /deny

The web

  • web_fetch reads a public page as Markdown; web_search uses DuckDuckGo with no key, or SearXNG, Brave or Tavily
  • Asks first by default; list trusted hosts to skip the question
  • Private, loopback and cloud-metadata addresses are refused, after DNS and on every redirect

Photos, PDFs and voice

  • Send photos, PDFs, text and CSV files; models that support images and PDFs receive them natively
  • Voice notes are transcribed by an OpenAI-compatible endpoint or a local command, if you configure one
  • send_file returns workspace files to your chat, with your approval

Reminders and schedules

  • Ask in chat: "remind me at 5pm", "every weekday at 9 summarize my notes"
  • Reminders never call the model; script-only jobs message you only when there is output
  • Cron jobs and heartbeats with cheap pre-checks, budgets, catch-up and pause-on-failure
  • send_message lets it reach paired chats on its own, with approval and a rate limit

Memory and skills

  • Bounded MEMORY.md and USER.md, versioned, frozen into each session
  • Skills in the open SKILL.md format, with provenance; ones you edit are locked against the agent, which can only propose changes
  • Compaction keeps the recent tail and your constraints

Models and keys

  • Anthropic, OpenRouter, local servers (Ollama, LM Studio, llama.cpp, vLLM) or any OpenAI-compatible API
  • Keys live in an encrypted store (AES-256-GCM, scrypt), in a mode-600 env file, or in your environment. Config stores only the name
  • Per-task budgets for model calls, tokens, tool calls and time

Setup and upkeep: garnet setup is a guided, re-runnable wizard, garnet doctor checks the install and says how to fix what it finds, and garnet service install keeps it running under systemd or launchd. Backup and restore are built in.

Security posture

Defaults you would choose yourself.

Nothing here is a promise that Garnet cannot be fooled. It is a set of small, checkable rules in the code, so a mistake costs less.

  • Commands denied by defaultWhen you allow them, they run in a Docker container: non-root, no network unless you enable it. The local backend exists but is not a security boundary, and says so.
  • Prompt-injection containmentAfter a conversation reads a web page or search results, actions that could do harm or leak data ask first, even ones you set to allow, until you send /new. The approval says why.
  • SSRF guardWeb tools reach only public addresses, with DNS pinned and every redirect re-checked.
  • Approvals you can seeApprove or deny in the terminal, in chat with /approve and /deny, or in the dashboard. The full operation is shown first.
  • Pairing, not open doorsUnknown senders get a pairing code you approve from the CLI. Messages to others go only to paired chats.
  • Workspace containmentTools touch only ~/.garnet/workspace. A workspace that would contain Garnet's own config and secrets is refused.
  • API behind keysOff by default. No public bind until a key exists, and the one-time dashboard link expires in 15 minutes.
  • An append-only logThe event log is never rewritten; cleaned views are derived from it. Secrets stay out of config, prompts, logs and tool output.
Compared with OpenClaw and Hermes

Different bets, stated plainly.

OpenClaw and Hermes Agent are larger, more established projects with wider reach. Garnet is smaller on purpose and younger. This table describes Garnet; where it falls short of them, it says so.

Switching

Bring your agent with you.

garnet import openclaw or garnet import hermes previews what it can bring over, and changes nothing until you confirm. It never copies secrets.

  1. PreviewA dry run shows what would come across, what would be skipped and why.
  2. ImportMemory (with bigger caps if yours was larger), persona and name, skills with their requirements flagged, and the people on your allowlists, paired only if you say so.
  3. ReviewScheduled jobs and heartbeat checklists arrive disabled so you can check them first. Skills that need host tools say so.

garnet setup offers the same import when it finds an existing OpenClaw or Hermes home. Run garnet import --help for the flags that decide how memory, persona and pairings are merged.

Install

One line. No sudo.

You need Node.js 22.18 or newer and git. The installer tells you how to get Node.js if it is missing.

It clones Garnet into ~/.local/share/garnet, adds a garnet command to ~/.local/bin and starts garnet setup: pick a model, paste your key (stored encrypted, never in config), name your assistant, connect a channel, install the service and pair your own account. Everything Garnet keeps is in ~/.garnet. Run the installer again to update; it leaves local changes alone.

Prefer to read first? git clone https://github.com/2180719/Garnet, then npm install and npm link. Try it with no key at all: garnet chat --fake.

FAQ

Questions people ask.

Is it ready to rely on?

Not yet. It is pre-release. The offline test suite is extensive, and live Anthropic chat, streaming, tools, prompt caching and dashboard chat have been verified on a Linux host. Telegram, Signal and Discord need more live testing, so expect rough edges the first time it meets a real bot.

Where does my data go?

Conversations, memory and files stay in ~/.garnet on your machine. Your messages go to whichever model provider you pick, and to the messaging platform you use. Garnet has no telemetry, and this website sets no cookies.

What does it cost to run?

Garnet is free and open source (Apache-2.0). You pay your model provider, or nothing if you use a local model. Each task has token, call and time budgets, and /usage shows what a conversation has used.

Can it run commands on my computer?

Only if you allow it. Commands are denied by default and, when allowed, run in a Docker container without network access. The local backend runs on your host and is not a security boundary.

Which models work?

Anthropic, OpenRouter, local servers such as Ollama, LM Studio, llama.cpp and vLLM, and any OpenAI-compatible API. Image and PDF input depends on the model.

Is it related to Ruby the programming language?

No. Garnet was previously named Ruby and is unrelated to the language. Its command is garnet, so it will not collide with the ruby interpreter.
